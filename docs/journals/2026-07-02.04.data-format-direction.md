# Data Format Direction

Synthesizing the Wikidata Discord conversation (`2026-07-02.01`), the Claude web conversation on Popolo and standards (`2026-07-02.03`), and independent research on election data standards (`2026-07-02.02`).

## Current state

Raw CSVs/DOCX → Python ETL → SQLite staging DB (14 tables) → JSON exports for the Next.js site. One election cycle parsed (NA15-2021), stubs for NA14-2016 and NA16-2026. Per-field source citations, document terms, and derived-vs-stated annotations throughout.

## The two-layer split

Entity data (persons, orgs, areas, memberships) and quantitative returns (vote counts per candidate per constituency) are fundamentally different shapes. The entire field has converged on this — nobody puts vote tallies in a graph. Our SQLite schema already embodies this naturally.

## Standards landscape (summary)

- **Popolo** — Person/Organization/Membership/Area vocabulary. Good for the entity layer. Dormant ecosystem (EveryPolitician sunset ~2019). Cannot represent candidacies, vote counts, or losers — only winners as Memberships. Posts don't work for multi-member constituencies.
- **NIST SP 1500-100** — Most comprehensive election results standard (CandidateContest, VoteCounts, ReportingUnit). U.S.-centric, heavy UML-derived schema.
- **OpenElections / MEDSL** — Flat CSV, one row per candidate-per-contest-per-geography. The field's revealed preference for returns data.
- **OCD Division IDs** — Semantic, hierarchical geographic identifiers. U.S.-centric registry.
- **W3C PROV-O** — Our annotations/sources pattern is a subset of this. Worth aligning field names for machine-interoperability.

None of these handle Vietnam's single-party nomination/vetting process, multi-member approval voting, or per-field provenance.

## Direction

### What stays the same

- **SQLite as the single source of truth** for the ETL pipeline. Everything else derives from it.
- **Git repo as the immutable archive.** Wikidata and Commons are distribution channels, not the system of record.
- **JSON exports shaped for the website** — nested, provenance-rich, consumed by the Next.js frontend.
- **Provenance model** — per-field source citations, document terms, derived-vs-stated annotations. This is the project's differentiator. Protect it, don't flatten it.

### What to add

1. **Fix the `candidate_entry_id` doubled prefix bug.** All 866 records have `na15-2021-na15-2021-...`. One-liner in the generator, but nothing should be built against a malformed key.

2. **JSON Schema for the three JSON exports** (results, constituencies, localities) with shared definitions. Validates in CI, catches regressions, defines the public contract. The Claude web conversation already drafted these against live data and found the ID bug plus mixed constituency ID grammars (`na15-2021-const-N` vs `const-auto-<hash>`).

3. **CSV flat exports** — one row per candidate-result, auto-generated from SQLite, with a companion codebook. This is the highest-impact accessibility move. Researchers want `read.csv()`, not nested JSON. OpenElections and MEDSL converged on this shape for good reason.

4. **`datapackage.json`** (Frictionless Data descriptor) — bundles schema, licensing, and file descriptions. Turns "pile of files in git" into a self-describing dataset. R's `frictionless` package can ingest it directly.

5. **Adopt Popolo field names in-place** in the existing JSON exports where they map naturally — `name` instead of `full_name`, `identifiers` array with `{scheme, identifier}` for external IDs. We already use `sources`, which is Popolo-native. No separate Popolo export pipeline.

6. **Backfill external identifiers** — Wikidata QIDs on persons (cheap join key to linked data), ISO 3166-2:VN on provinces pinned to as-of-2021 boundaries (Vietnam is merging administrative units). High interop value per hour.

7. **Zenodo or Dataverse deposit** — DOI for citation, versioned snapshots. More valuable for an archival project than Commons tabular data.

### What to deprioritize

- **Separate Popolo JSON export.** Dormant ecosystem, no consumers, maintenance cost for a solo maintainer. Borrow the vocabulary in-place instead.
- **Extension profile spec** for candidacy/multi-member/single-party semantics. Premature with one election cycle. Build the schema for the data we have; call it a spec once NA14 and NA16 have validated the shape.
- **Commons `.tab` upload.** Niche audience, mutable (not an archive), flattens provenance to a single `sources` text field. Only worth doing after everything above, as a thin derivative that points home.
- **OCD Division IDs.** U.S.-centric registry, and Vietnam's admin units are being reorganized. Our opaque hashes + ISO 3166-2:VN anchors are more honest.

## Sequencing

Cheapest-and-most-foundational first:

1. Fix `candidate_entry_id` bug
2. JSON Schema + CI validation
3. CSV flat exports + codebook
4. `datapackage.json`
5. Popolo field name alignment in existing JSON
6. Identifier backfill (Wikidata QIDs, ISO 3166-2:VN)
7. Zenodo/Dataverse deposit

## One-sentence version

The repo is already the right architecture — add flat CSVs for researchers, a JSON Schema for validation, and a `datapackage.json` to make the whole thing self-describing; borrow Popolo vocabulary in-place rather than building a parallel export nobody consumes.
