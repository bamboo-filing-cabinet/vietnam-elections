# Raw Data Archival Plan

Date: 2026-07-07
Related issues: #36 (baucuquochoi), #38 (dbqh)

## The problem

We have ~1.4 GB of raw HTML profile pages and ~8,000 candidate photos hosted on external CDNs. The HTML is saved locally but gitignored. The photos haven't been downloaded yet. Both source sites (baucuquochoi.vn and dbqh.quochoi.vn) are government-operated and could be restructured, redesigned, or taken offline without notice.

Three goals:
1. **Preservation** — durable backup in case source sites disappear
2. **Reproducibility** — others can verify our parsed JSON against the originals
3. **Completeness** — capture photos before CDNs rotate or expire

HTML compresses extremely well: 545 MB → 60 MB (89%) and 864 MB → 112 MB (87%). This is because profile pages share a massive boilerplate (nav, footer, scripts) with only a small content area differing per delegate.

## Options considered

### Option 1: Git LFS in a separate repo

Create `vietnam-elections-archive` as a submodule in the monorepo. Track raw HTML and photos with Git LFS.

- **Pros:** Version-controlled, familiar git workflow, integrates as submodule alongside vietnam-elections and vietnam-elections-wikidata.
- **Cons:** GitHub's free LFS tier is 1 GB storage + 1 GB/month bandwidth. Our raw HTML alone is 1.4 GB, which exceeds the free tier. Need a $5/month data pack (50 GB) or a self-hosted LFS server. Every `git clone` by a collaborator pulls all LFS objects and counts against bandwidth.
- **Mitigation:** Store compressed tarballs (172 MB for HTML) instead of individual files. This fits comfortably in the free 1 GB tier and reduces bandwidth. Individual files can be extracted locally. Trade-off: lose per-file git history and diffing, but we don't really need that for raw HTML dumps.

### Option 2: GitHub Releases (no LFS)

Same separate repo, but attach data as tarballs to tagged releases instead of tracking in LFS.

- **Pros:** Free with no storage or bandwidth limits on release assets (2 GB per file). No cost. Easy for researchers to download a specific crawl snapshot.
- **Cons:** Not version-controlled in the traditional sense — releases are append-only snapshots, not diffs. Harder to browse individual files without downloading the full tarball. Releases aren't cloned with the repo.
- **Structure:** Tag each crawl as a release (e.g., `baucuquochoi-2026-07-07`, `dbqh-2026-07-07`). Attach `.tar.gz` files organized by source and term.

### Option 3: Internet Archive upload

Upload WARC files or tarballs to archive.org via their S3-like API.

- **Pros:** Truly permanent, free, public good, no maintenance, machine-readable via API. Gets a permanent URL and can be cited.
- **Cons:** Upload is one-way and slow. Not git-integrated. Can't easily update or reorganize. We'd still want a local copy for development.
- **Best for:** Long-term preservation after we've stabilized the data. Complement to, not replacement for, a git-based solution.

### Option 4: Zenodo deposit

Bundle as a research dataset with DOI.

- **Pros:** Citeable, permanent, up to 50 GB per dataset. Academic credibility.
- **Cons:** Same as Internet Archive — one-way, not git-integrated. Better suited for versioned releases of processed data than raw HTML dumps.
- **Related:** Already tracked in #31 for the processed/exported data. Raw HTML could be included as supplementary material.

### Option 5: Object storage (S3/R2/B2)

Host on Backblaze B2 (~$0.005/GB/month) or Cloudflare R2 (free egress).

- **Pros:** Cheapest at scale, no limits, fast.
- **Cons:** Requires infrastructure (API keys, bucket management), not discoverable, not self-documenting. Overkill for our current scale.

## Two distinct problems

The initial instinct was to treat this as one archival problem, but there are actually two:

1. **Archival** — durable backup of raw HTML in case source sites disappear. We don't serve HTML to users; it's for reproducibility and verification. Tarballs are fine.
2. **Serving** — candidate photos displayed on the vietnam-elections static site. These need to be individually addressable by URL. A tarball doesn't work here.

These need different solutions.

## Recommendation: separate repo with two storage strategies

### `vietnam-elections-archive` repo

A new repo in the monorepo, structured like:

```
vietnam-elections-archive/
├── README.md
├── .gitattributes              # LFS tracking rules
├── baucuquochoi/
│   ├── fetch-profiles.py       # (moved from vietnam-elections)
│   ├── html/
│   │   ├── xiv.tar.gz          # 279 profiles, LFS-tracked
│   │   ├── xv.tar.gz           # 631 profiles, LFS-tracked
│   │   └── xvi.tar.gz          # 866 profiles, LFS-tracked
│   └── photos/
│       ├── {source_id}.jpg     # Individual files, NOT tarballed
│       └── ...
├── dbqh/
│   ├── fetch-term.py           # (moved from vietnam-elections)
│   ├── html/
│   │   ├── I.tar.gz            # 415 profiles
│   │   ├── ...
│   │   └── XV.tar.gz           # 499 profiles
│   └── photos/
│       ├── {term}/
│       │   ├── {delegate_id}.jpg
│       │   └── ...
│       └── ...
└── manifests/
    ├── baucuquochoi.csv         # source_id, term, filename, sha256, photo_url
    └── dbqh.csv                 # term, delegate_id, filename, sha256, photo_url
```

### HTML → compressed tarballs in LFS

Raw HTML is for archival only — nobody browses it on the web. Tarballs compress ~90% (1.4 GB → 172 MB) and fit comfortably in GitHub's free 1 GB LFS tier.

**Why LFS, not regular git:** Regular git stores full file contents in history. LFS stores a pointer in git and the blob externally. Keeps `git clone` fast for people who don't need the raw data.

### Photos → individual files, NOT tarballed

Photos need to be individually addressable so the vietnam-elections site can reference them. Several options for serving:

**Option A: GitHub Pages on the archive repo.**
Enable Pages on `vietnam-elections-archive`. Photos become available at URLs like `https://bamboo-filing-cabinet.github.io/vietnam-elections-archive/baucuquochoi/photos/406.jpg`. The vietnam-elections site references these URLs. Free, no infrastructure.

Caveat: GitHub Pages has a soft 1 GB repo size limit and 100 GB/month bandwidth. ~8,000 photos at ~50 KB average = ~400 MB, which fits. But LFS-tracked files are NOT served by GitHub Pages — so photos must be regular git objects, not LFS. This works if photos are small (they are — JPEG portraits at 20–100 KB).

**Option B: Cloudflare R2 or similar CDN.**
Upload photos to object storage with a custom domain. More scalable, free egress on R2. But requires infrastructure and credentials management.

**Option C: Keep hotlinking source CDNs, archive separately.**
The vietnam-elections site continues to reference `cdnimage.daihoidang.vn` URLs. The archive repo stores copies for preservation. If the CDN goes down, we switch to self-hosted. Pragmatic but fragile.

**Option D: Photos in vietnam-elections/public/.**
Download photos directly into the static site's public directory. Simplest for the build pipeline — no cross-origin, no external dependencies. But adds ~400 MB of images to the main repo.

**Leaning toward: Option A (GitHub Pages on archive repo).** It's free, requires no infrastructure, and separates concerns — the main repo stays lean, the archive repo serves double duty as both backup and CDN. The vietnam-elections site can reference photo URLs at build time.

If the site grows and bandwidth becomes an issue, we can migrate to Option B (R2) later without changing the URL structure.

### Secondary: GitHub Releases for bulk distribution

Tag releases with the crawl date. Attach tarballs (HTML + photos) for researchers who want everything in one download. This is a convenience layer.

### Tertiary: Internet Archive for permanence

Once we're confident in the data, upload to archive.org. This is the "it'll outlive us" tier. Not urgent — do after the first stable release.

## Sequencing

1. **Now:** Download photos from both sources (write fetch scripts)
2. **Soon:** Create `vietnam-elections-archive` repo — compress HTML into tarballs (LFS), commit photos as individual files, enable GitHub Pages, add manifests
3. **Soon after:** Update vietnam-elections site to reference archive repo photo URLs instead of external CDNs
4. **Later:** Upload to Internet Archive and/or Zenodo (#31)

## Open questions

- Should fetch scripts live in the archive repo or stay in vietnam-elections? Argument for archive: they produce the raw data stored there. Argument for vietnam-elections: they're part of the data pipeline. Leaning toward archive repo since the scripts are source-specific, not pipeline-specific.
- Should we also archive the listing pages (already committed to vietnam-elections)? They're small — could go either way.
- Do we need to re-crawl periodically? baucuquochoi.vn may update profiles (e.g., new positions). If so, versioned tarballs per crawl date make sense.
- The na16-2026/results/profiles/ directory (500 XVI winner profiles, 303 MB) overlaps with baucuquochoi-profiles/raw/ (which has all 866 XVI profiles). Should we deduplicate? Probably just drop the separate winner profiles and use the complete set.
- For GitHub Pages serving, should photos be organized by source_id (flat) or by term? Flat is simpler for cross-term lookups; by-term matches our data structure.
- Photo naming: use source IDs from each site, or normalize to our person_id? Source IDs are simpler and don't require the mapping step, but person_id would make cross-referencing easier. Probably source IDs for now, with a manifest CSV that maps to person_id.
