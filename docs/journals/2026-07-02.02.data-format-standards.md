# Data Format Standards for Election Data

Prompted by a Wikidata Discord conversation (see `2026-07-02.01.wikidata-discord-conversation.md`) and a suggestion to look at the Popolo Project.

## Our current data model

SQLite database (`data/staging.db`) built by Python ETL from raw CSVs/DOCX. 14 tables covering:

- **Election cycles** — one so far (NA15-2021), with date ranges
- **Geography** — locality (province/city) → constituency (numbered unit, with seat count) → constituency_district
- **People & candidacies** — person → candidate_entry (per cycle/constituency) → candidate_attribute (EAV for education, occupation, etc.)
- **Results** — election_result_candidate (votes, percent) → annotation (won/lost/not_confirmed with reason and effective_date); election_result_summary (turnout, valid/invalid votes)
- **Provenance** — document → document_terms (licensing); source (per-field citations linking record+field → document)

The exported JSON files in `public/data/` are shaped for the UI, not for interchange.

## Standards landscape

### Popolo (popoloproject.com)

13 entity classes across three domains:

| Domain | Classes |
|---|---|
| People & organizations | Person, Organization, Membership, Post, Contact Detail |
| Legislative voting | Motion, Vote Event, Count, Vote |
| Other | Area, Event, Speech, Identifier |

**What it's good for:** Modeling who belongs to what body, with contact details and posts held. Person and Organization are well-specified and widely adopted (EveryPolitician used Popolo JSON).

**What it doesn't cover:** Candidate contests, vote counts per candidate, winner/loser status, turnout, multi-member districts, party vote totals, seat allocation. Its voting model is parliamentary (yes/no/abstain on motions), not electoral. `Count.option` only supports yes/no/abstain — no candidate dimension at all.

**Vietnam-specific gaps:** No concept of candidate vetting/screening (Fatherland Front nomination approval), no bloc-list approval voting, no nomination stages. All spec examples reference Western legislatures.

### Open Civic Data (OCD)

Stable identifiers for political geographies (OCD-IDs). Person, Organization, Membership, Bills, Votes — but like Popolo, the vote model is legislative, not electoral.

**Useful for:** Borrowing the division ID scheme for our provinces/constituencies if we want external interoperability.

### OpenElections Results Data Spec v2

CSV schema for candidate-level results: vote counts, winner status, party, district. Uses OCD-IDs for jurisdictions.

**Limitation:** U.S.-centric. No modeling of nomination stages or non-plurality systems.

### NIST SP 1500-100 Election Results CDF

The most comprehensive election results standard. JSON and XML schemas from UML. Entities include `CandidateContest`, `Candidate`, `Party`, `ReportingUnit` (precinct/county/state), `VoteCounts`, `BallotCounts`. Supports winner/defeated/withdrawn status, precinct-level counts, ballot type breakdowns.

**Limitation:** Designed for U.S. electoral administration. No modeling of candidate vetting/screening or approval-voting nomination as used in Vietnam.

## Assessment

| Our data need | Best existing standard | Gap? |
|---|---|---|
| Person, organization, membership | Popolo | Minimal — good fit |
| Electoral constituency / district | OCD Division IDs | Minimal |
| Candidate-level vote counts, winner status | NIST 1500-100 or OpenElections | Moderate — U.S. assumptions |
| Multi-member constituencies, seat counts | NIST 1500-100 | Moderate |
| Turnout, valid/invalid votes | NIST 1500-100 | Minimal |
| Source provenance per field | None of the above | We already do this better |
| Nomination/vetting stages (Fatherland Front) | Nothing | Custom extension needed |
| Document terms / licensing | Nothing | Custom extension needed |

## Takeaways

1. **Popolo is not an election results standard.** It's an organizational/membership + parliamentary voting standard. Useful as a vocabulary for Person and Organization, but not for the core of what we do (constituency-level candidate results).

2. **NIST 1500-100 is the closest fit for results data**, but it's heavy (full UML-derived schema) and U.S.-centric. Worth studying for its entity design, not necessarily adopting wholesale.

3. **Our provenance model is already ahead of all these standards.** Per-field source citations with document fetched dates, licensing terms, and the raw source preserved — none of the above standards track this. This is a strength to keep.

4. **No standard handles Vietnam's electoral specifics.** The single-party nomination/vetting process, bloc-list approval voting, and derived winner status are unique enough that any standard would need extension.

5. **Practical path forward:** Rather than adopting a standard wholesale, consider:
   - Align Person/Organization fields with Popolo naming conventions for interoperability
   - Adopt OCD-style division IDs if we want external systems to reference our constituencies
   - Keep our results schema as-is — it already handles what NIST does, minus the U.S. assumptions
   - Keep our provenance model — it's genuinely novel
   - If we want to publish interchange data, export Popolo-shaped JSON for persons/organizations alongside our results JSON

6. **Wikidata as a complement, not a replacement.** Per the Discord conversation: Wikidata is reasonable for the relational scaffolding (who ran, which office, which term) but poor for quantitative results and archiving. Our repo remains the archive; we could push person/organization stubs to Wikidata and link back.
